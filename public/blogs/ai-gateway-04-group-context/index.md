> 本系列以面向中国华能集团的企业知识助手为设计场景，业务对话均为示例。代码节选与结构示意用于说明设计原因、作用和取舍，省略了无关细节。

## “把刚才那个整理一下”，到底指什么

假设一个资料群里，大家聊了几句：

> 小李：去年的培训材料在旧目录。  
> 小王：我刚发的 PDF 是更新版。  
> 小张：@助手，把刚才两份资料的差别整理一下。

如果机器人只把最后一句交给模型，“刚才两份”就没有具体指向。

反过来，如果把群里每句话都立即送给模型，机器人会频繁插话，普通聊天也会制造调用成本。更麻烦的是，无关对话可能持续进入长期记忆。

这不是简单增加一个“支持群聊”的开关就能解决的事。我会先拆成三个问题：**看得到什么、什么时候回答、回答时带上什么。**

## 三个问题分别配置，才不会互相绑死

| 维度 | 它回答的问题 | 示例 |
| --- | --- | --- |
| visibility | 平台会给机器人哪些消息 | 全部可见，或只能看到 @ |
| activation | 收到什么消息才开启一次处理 | 被 @ 才答，或每条都答 |
| history | 触发时是否附带短期讨论 | 带最近几条，或不带 |

这里最容易被忽略的是第一项。机器人愿意听，并不代表平台有权把所有消息发给它。

在这套设计中，`GroupContextConfig` 将这些维度分开。默认关闭群聊上下文；启用后，还可以针对具体群覆盖策略。这样，资料讨论群和通知群不必使用完全相同的规则。

我会从“被 @ 才回答，适量带最近讨论”开始试用，再根据实际反馈调整。至于可见性，必须以平台授权与实际事件为准。

## 未触发的消息，先放进短期缓冲

当前策略的主线很直观：

![被动讨论进入缓冲，被 @ 后附带上下文](/blogs/ai-gateway-04-group-context/group-flow.svg)

[下载群聊处理图的 Mermaid 源文件](/blogs/ai-gateway-04-group-context/group-flow.mmd)

未触发的消息可以进入 `GroupContextManager` 的内存缓冲，返回 `None`，不启动处理器。真正被 @ 时，才把最近讨论作为 `GroupContext` 附在本轮消息上。

这种“最近讨论”和长期对话历史是两回事。

短期讨论帮助理解“刚才那份资料”，没有必要因为被机器人看见，就自动变成长期记忆。持久化保存什么，仍由宿主应用和处理器决定。网关提供了短期上下文，也不意味着宿主可以忽略自己的保留策略。

配置示例：

```python
group_context = GroupContextConfig(
    enabled=True,
    visibility="mention_recent",
    activation="mention",
    history="recent",
    history_limit=10,
    history_ttl_seconds=300.0,
    clear_after_reply=True,
)
```

这里的 10 条和 300 秒是项目默认量级的示例，不是业务调研得到的最佳值，也不是对所有企业群的推荐标准。

## 让代码先做触发判断，而不是让模型决定是否插话

一种看似省事的方案，是把所有可见群消息都送进模型，再提示模型“你觉得不需要回答时就别回答”。这能把规则藏进提示词，却已经发生了一次调用，还让是否触发变成不稳定的生成结果。

如果产品规则明确是被 @ 才回复，就应该在模型之前判断。下面是保留关键分支的流程示意，枚举比较和上下文封装做了简化：

```python
def prepare(self, message):
    conversation_id = self._conversation_id(message)
    policy = self._config.resolve(conversation_id)

    if not policy.enabled:
        message.group_context = None
        return message

    self._expire(
        conversation_id,
        policy,
        now=message.timestamp,
    )

    activation, degraded = self._effective_activation(policy)
    mentioned = bool(message.metadata.get("bot_mentioned"))
    should_process = activation == "always" or mentioned

    if not should_process:
        if (
            policy.visibility != "mention_only"
            and policy.history == "recent"
        ):
            self._append(conversation_id, message, policy)
        return None

    return self._attach_context(message, policy, degraded)
```

示例中的 `_attach_context` 是为了压缩讲解而提取的占位职责，实际实现可以在当前方法内组装上下文。关键是判断的先后关系：先应用策略、清理旧项，再判断触发；未触发时按配置保留讨论，然后结束。

这样做带来三个直接作用。首先，普通闲聊不会消耗一次模型请求。其次，同样的输入和配置能得到确定的触发结果。最后，测试不必依赖模型措辞，只需要检查处理器有没有被调用、缓冲有没有变化。

“被 @”本身也应由适配器识别平台提供的事实，而不是简单在文本里搜索机器人的名字。昵称可能被复制，消息里的文字也可能只是引用。平台原生的 mention 标识通常更适合表达这类语义。

## 配置覆盖为什么要有固定顺序

同一个机器人可能进入多个群。资料讨论群希望带上最近聊天，通知群只希望处理明确提问。如果为每个群都复制一份完整配置，后面调整公共默认值会很麻烦。

我会采用“默认配置 → 通配覆盖 → 指定群覆盖”的顺序。公共项只写一次，少量例外在对应群里声明。

```python
config = GroupContextConfig(
    enabled=True,
    activation="mention",
    history="recent",
    history_limit=10,
    groups={
        "*": {"history_ttl_seconds": 300},
        "announcement-group": {"history": "none"},
        "document-group": {"history_limit": 6},
    },
)
```

`announcement-group` 只覆盖历史模式，其他字段继承公共值；`document-group` 只调整条数。固定覆盖顺序能让管理员推断最终行为，也便于界面展示“这一项来自哪里”。

不过，配置修改后不能只考虑下一条消息。比如某个群从保留历史改为不保留，已有缓冲是否需要立即清理？如果只是停止追加，旧内容可能仍留在内存里。

因此，权限或保留策略收紧时，应有清理现有上下文的路径。策略变更是一个状态转换，不只是改一个字典字段。清理内存讨论与删除持久化附件仍是两件事，后者需要独立的保留机制。

## 同一条群消息，要保留两个身份

小李提问，小王补充，两人处在同一个群里。会话目标应当是这个群，但上下文还必须知道哪句话由谁说。

项目用群会话 ID 作为 `channel_subject.subject_id`，作者信息放在 metadata，缓冲后保留到 `GroupContextMessage` 中。

这避免了两种错误：一是按作者把同一个群拆散；二是把全部内容合成一段文字，丢掉作者归属。

后续把群聊交给模型时，我会把这些内容作为带来源的上下文组织，而不是把某个群成员的发言提升成系统指令。例如，“忽略所有规则”即使出现在最近聊天中，也只是用户内容，不能改变助手权限。

这是模型输入边界的设计要求，不能仅靠有了群聊缓冲就自动实现。

## 条数、时间和清理，分别控制不同问题

项目提供三类保留边界：

- `history_limit` 限制本次可附带的最近消息条数。
- `history_ttl_seconds` 让过旧的上下文失效。
- `clear_after_reply` 在成功处理后清理一次性缓冲。

条数解决“内容太多”，TTL 解决“指代已经过时”，回复后清理解决“同一批闲聊反复附带”。

![短期讨论的保留与清理](/blogs/ai-gateway-04-group-context/context-life.svg)

[下载上下文生命周期图的 Mermaid 源文件](/blogs/ai-gateway-04-group-context/context-life.mmd)

这些限制也有实现边界。当前过期检查由后续消息触发，并不是每到五分钟就由后台定时任务立即清除内存。群很多时，缓冲字典的总体规模也值得评估。

在公共入站链路里，只有处理成功才调用 `mark_replied`。失败时保留上下文，可以给后续尝试留下信息；不过“成功处理”仍然是程序状态，不等于证明终端用户已经读到了全部内容。

## 为什么缓冲里要复制媒体内容

如果缓冲直接引用入站消息里的同一份媒体对象，后续流程修改它的 URL、存储键或其他字段时，已经保存的上下文也会跟着变化。这种问题通常没有明显报错，却很难解释“之前那条消息为什么变了”。

保留上下文时，可以复制内容描述，形成当前时点的快照：

```python
content = [
    part.model_copy(deep=True)
    for part in message.content
    if not isinstance(part, TextContent)
]

entry = GroupContextMessage(
    message_id=str(message.metadata.get("message_id") or ""),
    sender_id=str(message.metadata.get("sender_id") or "unknown"),
    sender_name=str(message.metadata.get("sender_name") or ""),
    text=message.text.strip(),
    content=content,
    timestamp=message.timestamp,
)
```

这里复制的是内容对象，不代表把整份附件字节再存一遍。只要媒体部分保存的是存储键，缓冲可以保留这个键，再由存储后端提供实际内容。

代价是多了一份描述对象，以及可能重复持有的内联数据。对于很大的 base64 字段，我会尽量在进入长期等待的缓冲前持久化为存储键，并评估是否还需要保留原始数据。这是内存使用上的设计取舍，不是深复制本身能自动解决的问题。

文字和附件也不能只取其一。纯文件消息可能没有正文，但仍然为下一句“总结刚才那个”提供了必要指代。

## TTL 为什么不等于一个定时删除器

最容易理解的 TTL 实现，是新消息到来时，检查队首是否过期：

```python
def expire(buffer, now, ttl_seconds):
    cutoff = now - ttl_seconds
    while buffer and buffer[0].timestamp < cutoff:
        buffer.popleft()
```

这个示例只展示时间裁剪，假定队列按时间递增。消息很多时，从队首弹出比每轮全量扫描容易控制成本；消息不多时，实现也足够直观。

它的前提需要说清。如果平台事件会乱序，过期消息不一定集中在队首；如果平台时间明显漂移，按事件时间计算的五分钟也未必等于本机观察到的五分钟。

因此，我会先明确时间字段的来源和排序条件。对于只关心本机保留时长的缓冲，可以另外记录接收时刻；如果要按业务事件时间理解讨论，就要决定如何处理迟到消息。这是后续强化方向，不应把当前简单裁剪描述成已经解决全部乱序问题。

惰性清理的好处是无需为每个群维护定时任务，生命周期管理比较简单。代价是一个再也没有消息的群，过期项可能仍在内存中等待清理。群数量很大、保留要求严格时，再增加周期巡检更合理。

## 条数限制之外，还要考虑上下文体积

“最多十条”容易理解，却不代表成本固定。一条消息可以只有几个字，也可以是一段很长的文档摘录。十条长消息和十句短对话，对模型输入的影响完全不同。

因此，我会把条数作为第一层限制，业务处理器再按实际模型的输入预算整理内容。优先保留与当前问题有明确指代关系的附件或最近发言，其余内容可以截断或省略，并让处理器知道上下文可能不完整。

这里不必一开始就加入模型摘要。让另一个模型总结闲聊，会增加调用、延迟和事实压缩风险。先用明确的条数、时间和体积边界控制成本，等观察到真实需求，再决定是否引入摘要。

## 平台看不见的内容，不能靠配置补出来

假设配置写着“每条消息都回答”，平台却只推送 @ 事件。代码无法处理它根本没有收到的消息。

项目在 `activation="always"` 且可见性没有明确为 `all` 时，会退回 mention 激活方式，并设置 `capability_degraded`。

我认为这个字段很有价值：配置被保留，真实能力也被如实表达。管理界面可以告诉维护者“当前平台能力不足，已按 @ 触发”，避免把少收到的消息误判为程序丢消息。

同样，`mention_only` 模式不会保留被动闲聊，也不会凭空产生历史。理解能力应当建立在真实可见范围内。

## 群里只发一份文件，也算上下文

前面例子里的 PDF 可能没有配文字。如果缓冲只保存 `message.text`，机器人到了下一轮仍然不知道大家在说哪个附件。

项目会把内容部分保留进群聊上下文，支持只含文件的被动消息。公共准备流程会在需要保留时，先持久化媒体，再写入短期缓冲，避免只留下一条可能过期的下载链接。

同时，历史关闭或 mention-only 等策略下，没有必要为了最终会被丢弃的被动附件，先做一轮无意义下载。是否保存媒体也需要受群聊策略控制。

这段流程应按渠道检查。当前企微有独立的 `handle_inbound` 实现，没有完整复用这套群聊准备与收尾逻辑，因此不能据此宣称所有渠道都已经具有同样的上下文行为。

## 一段群聊，怎样变成有来源的模型输入

我不想把缓冲里的全部文字直接塞进系统提示词。那样会模糊“系统规则”和“群成员发言”的区别，也容易把普通消息理解成高优先级命令。

更清楚的组织方式，是让处理器接收带作者、时间和内容类型的材料。例如下面是逻辑结构示例，并非某个模型 API 的固定参数格式：

```python
context_items = [
    {
        "source": "group_message",
        "sender": item.sender_name or item.sender_id,
        "timestamp": item.timestamp,
        "text": item.text,
        "attachments": [
            part.model_dump()
            for part in item.content
        ],
    }
    for item in message.group_context.messages
]
```

结构保留了可追溯的来源。模型看到“小王发来 PDF”和“小张请求比较”时，才有机会正确理解二者关系。至于附件是否能被当前用户读取，还应由处理器按业务权限判断，不能因为它曾出现在同一个群，就自动认为可以发给任何私聊用户。

重复消息也值得处理。平台重连或补发历史时，同一条消息可能既来自平台附带的近期列表，也来自本地缓冲。优先用消息 ID 去重，比按文字去重更可靠，因为两个人说了同一句话，并不代表是同一个事件。

没有消息 ID 时，可以退回到作者、内容和附件描述组成的近似键，但要接受它只是折中。同一作者重复确认一句话，仍可能被误判为重复，因此不应该拿这种近似去重承担严格业务审计。

## 为什么先保留失败后的上下文

设想机器人已经读到了两份资料，模型服务临时不可用。如果失败路径把缓冲全部删掉，用户紧接着说“再试一下”，系统只剩“再试一下”四个字。

成功后清理、失败时暂时保留，能让重试更符合用户预期。但这并不是无限期重试保证，TTL 和条数限制仍然生效。真正重要的业务任务，应当把任务状态与资料引用存到专门的数据层，而不是依赖短期聊天缓冲。

同样，清理策略要和交付语义对应。如果处理器已经成功，但部分平台发送失败，是否算一轮成功，需要交付结果模型表达得更细。一个布尔值适合简单阶段；出现部分成功需求时，就应考虑把“处理完成”和“全部发送完成”分别记录。

## 用几段对话就能检验设计

我会先跑通以下对话：

1. 两个人正常讨论，再有第三个人 @：附带讨论，保留作者。
2. 只允许 @ 可见：不生成不存在的历史。
3. 讨论超过 TTL 后再 @：旧消息不再附带。
4. 成功回复后再次 @：上一批已清理的讨论不重复出现。
5. 先发文件再提问：上下文仍然包含文件内容描述。
6. 指定某个群关闭 history：不影响其他群。

仓库的 `tests/test_group_context.py` 已有对应的多项行为测试，包括能力降级、过期清理、每群覆盖和只含文件的消息。

这一篇的核心是群聊策略模块、上下文消息模型和公共入站准备流程。配置与代码示例服务于设计说明，真实平台可见性需要在接入时核实。

一个好用的群聊助手，不需要时时证明自己在线。它应该在被需要的时候，接得上眼前这段讨论。
