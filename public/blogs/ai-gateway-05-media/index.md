> 本系列以面向中国华能集团的企业知识助手为设计场景，业务对话均为示例。代码节选与结构示意用于说明设计原因、作用和取舍，省略了无关细节。

## 对用户来说，只是发了一张图

员工在群里发来一张软件报错截图：“这个提示是什么意思？”

对用户来说，操作已经结束；对系统来说，工作才刚开始：平台给的是公开地址、带鉴权的下载地址，还是需要交换的媒体标识？链接多久会过期？读取完以后存在哪里？助手生成一份文件，又该怎么发回去？

如果只把文字收发跑通，然后把图片看成“多一个 URL 字段”，附件很容易在中间某一步失去实际内容。

我会沿着字节的路径设计这部分：**从平台拿到数据，必要时保存，处理后交给目标平台。**

## 先统一“内容是什么”，再决定“字节在哪里”

项目把文字、图片、视频、音频和文件表达成不同的 `ContentPart`。媒体部分可以携带三种来源：

| 字段 | 含义 | 典型场景 |
| --- | --- | --- |
| `data` | base64 编码的字节 | 处理器刚生成了一张图片 |
| `local_path` | MediaBackend 管理的存储键 | 入站附件已经保存 |
| `url` | 远程地址 | 平台提供下载入口 |

这三个字段有时会同时存在，读取顺序必须明确。否则，生成了新图片却读到旧链接，或者已经有字节还重新走网络，行为就会变得不可预测。

当前 `load_media_bytes` 的顺序是 `data → local_path → url`。

![媒体字节来源的选择顺序](/blogs/ai-gateway-05-media/media-source.svg)

[下载来源选择图的 Mermaid 源文件](/blogs/ai-gateway-05-media/media-source.mmd)

它表达的含义是：有内存数据就先用内存数据；明确指定了存储键，就按这个键读取；只有前两种都没有时，才下载 URL。

## 把读取顺序集中在一个方法里，有什么实际作用

如果每个适配器都自己写一遍“先读文件，失败再下载”，不同渠道就可能对同一个内容对象作出不同选择。问题发生后，还要逐个平台排查到底读了哪份数据。

把规则集中到 `load_media_bytes`，可以让发送路径共享同一个来源契约。下面是聚焦优先级的简化实现，省略了 MIME 推断、缓存与异常包装：

```python
import base64


async def load_media_bytes(self, part):
    if part.data:
        raw = base64.b64decode(part.data)
        mime = part.mime_type or "application/octet-stream"
        return raw, mime

    if part.local_path:
        if self._media_backend is None:
            raise RuntimeError("Media backend is required")

        raw = await self._media_backend.read(part.local_path)
        mime = part.mime_type or "application/octet-stream"
        return raw, mime

    if part.url:
        return await self.fetch_remote_media(part.url)

    raise ValueError("No media source is available")
```

这里每个提前返回都在表达优先级：一旦选定高优先级来源，就不再尝试低优先级来源。特别是明确的存储读取失败，不应未经说明就换成 URL。否则可能把旧文件、远端更新后的文件或不同权限下的内容当成同一份附件。

这不意味着所有场景都禁止容错，而是容错必须符合产品语义。如果存储键只是一个可丢弃缓存，回源下载可能合理；如果它代表用户确认过的一份文件，回源替换就可能破坏一致性。接口需要先明确自己是哪一种。

集中读取还有一个收益：后面需要统计下载量、限制读取体积或增加存储访问记录时，可以在这条共同路径落实，而不是在十个适配器里各加一遍。

## 内存里有字节，为什么还要考虑大小

`data` 的好处是避免再次访问存储或网络。处理器刚生成一张图，直接交付最自然。

但 base64 不是免费的。编码后的长度通常约为原始字节的 4/3，也就是大约增加三分之一；这还没有计算字符串对象、JSON 包装和同时保留原始字节的开销。一个原始十几 MB 的文件，经过多份对象引用和序列化后，内存压力可能远高于文件本身。

因此，我会把内联数据定位为便捷路径，而不是所有文件的默认长期存放方式。小结果可以直接发，大附件更适合落到受控存储，并传递一个键。

上面的读取方法为了讲清优先级，没有加入完整的大小检查。实际部署需要在下载前、读取中和平台上传前分别评估限制。只看消息里声明的 `size` 不够，因为远端返回体可能与声明不一致。

对于大文件，如果平台和处理器都支持流式读写，再考虑分块传输。当前返回 `bytes` 的接口会把内容整体放入内存，不能因为外层是 async 就宣称已经是流式文件管道。

## local_path 这个名字，很容易让人误会

看到 `local_path`，我最初会想到 `C:\\files\\report.pdf` 这样的文件路径。但在这个接口里，它的语义是后端存储键。

例如：

```text
feishu/office-bot-01/training-summary.pdf
```

当后端是 `FileSystemMediaBackend` 时，可以把键映射到某个根目录下的真实文件；将来换成对象存储，渠道也不应该自己用 `open()` 读取它。

这里统一的是 `save`、`read`、`exists` 等存储契约，而不是承诺已经具备某种云存储实现。

如果 `local_path` 有值却没有配置后端，当前代码会抛出 `RuntimeError`，不会静默退回 URL。我认可这个选择：配置错误尽早暴露，比临时绕到网络下载更容易定位，也能避免把“我明确要求读取的那份内容”换成另一份。

如果需要文件系统隔离，我会显式指定媒体根目录。项目管理器未传后端时，会在启动阶段安装以 `/` 为根的文件系统后端；这项默认行为不等于已经做好企业部署的目录隔离。

## 后端接口为什么刻意只做存储

媒体后端要回答的是：这个键对应的字节能否保存、读取和检查存在。它不应该知道某个平台的 app secret，也不应该负责申请平台的图片 ID。

```python
from abc import ABC, abstractmethod


class MediaBackend(ABC):
    @abstractmethod
    async def save(self, data: bytes, key: str) -> None:
        ...

    @abstractmethod
    async def read(self, key: str) -> bytes:
        ...

    @abstractmethod
    async def exists(self, key: str) -> bool:
        ...
```

把接口收窄，有助于用内存后端做测试，也方便替换文件系统。实际的存储实现还可能提供本地路径辅助接口，但调用方不能假定所有后端都有磁盘文件。

这也说明接口名称无法替代能力说明。方法是 async，只意味着调用方用 await 调用；实现如果在事件循环里做同步大文件读写，其他任务仍然可能受影响。选择后端时，应检查实际 I/O 行为，而不仅仅看函数声明。

## 存储键要能区分来源，但不能承担全部权限语义

给键加上渠道类型、渠道实例和文件名，有助于避免同名附件互相覆盖，也便于定位来源。例如：

```text
feishu/office-bot-01/20261031/training-summary.pdf
```

这是便于阅读的示例，不是要求所有实现使用同一种精确命名规则。业务如果可能产生同名文件，还需要稳定消息 ID、随机标识或内容摘要等方式避免冲突。

路径分层只是命名空间，不是访问授权。知道键的处理器是否可以读、哪些用户能下载、何时清理，都应该有独立规则。多租户场景也不能只给目录加一个前缀，就认定其他代码不会越界读取。

我会避免把用户原始文件名直接当路径使用。文件名可以作为展示信息，真正存储键由系统生成或规范化，并核对解析后的路径仍位于允许根目录内。这既减少路径歧义，也让更换存储方式时不受本地目录规则牵制。

## 下载鉴权为什么留在平台层

同样一个 HTTPS 地址，有的平台可以直接 GET，有的平台必须加 token，还有的平台需要先用媒体标识换取下载入口。公共存储层无法可靠猜测这些规则。

适配器可以覆盖远程读取，下面是带鉴权下载的结构示例：

```python
async def fetch_remote_media(self, url):
    token = await self._refresh_token()
    http = await self._ensure_http()

    async with http.get(
        url,
        headers={"Authorization": f"Bearer {token}"},
    ) as response:
        response.raise_for_status()
        data = await response.read()
        return data, response.content_type
```

这样的分工让 token 刷新、HTTP 会话复用和平台错误留在同一个地方；公共层只需要得到字节与类型。默认的无鉴权下载仍然可以复用，不需要所有适配器都复制一遍。

不过，不能把“地址需要鉴权”理解成“任何传入地址都加上平台 token”。真实实现应确认下载目标属于受信任的平台资源，并考虑重定向行为，防止凭据被送到不相关的地址。这是下载入口需要单独验证的条件，不是上面几行示例已经完整实现的能力。

## 入站下载和出站上传，是两种不同能力

平台接收附件时，可能要求带 token 下载；向平台发送时，又可能要求先上传取得资源 ID。它们不必由同一个公共方法解决。

在项目里：

- `fetch_remote_media` 负责取得远程字节，平台需要鉴权时覆盖它。
- `_persist_media` 通过存储后端保存入站内容，把键写回媒体部分。
- `load_media_bytes` 负责统一出站读取。
- 平台自己的 `_send_media` 负责实际上传和发送。

![附件从平台进入、经过存储、再发回平台](/blogs/ai-gateway-05-media/media-flow.svg)

[下载媒体流转图的 Mermaid 源文件](/blogs/ai-gateway-05-media/media-flow.mmd)

图里的处理器表示业务接缝。读取截图、做 OCR、分析 PDF 或生成报告，需要处理器及其工具完成；网关传递附件，并不意味着自动理解了文件内容。

URL-only 的内容在出站读取时，如果配置了后端，还会尝试缓存并回写 `local_path`。缓存保存失败不会抹掉已经取到的字节。这里也应区分“发送内容已读取”和“缓存已经持久化成功”，不能只记录一个模糊的成功状态。

## 为什么我不想统一所有上传协议

统一读取之后，为什么不顺便做一个通用 `upload()`？

因为平台上的“上传成功”含义可能不同：拿到图片键、得到文件 ID、得到可发送资源，或者只是提供一个公网地址。把这些返回值硬塞进同一个类型，适配器很容易再次判断平台。

我更愿意让公共层只保证“给你内容字节与 MIME 类型”，其余留给平台实现。

在企业场景里，我会优先验证实际使用渠道的文字、截图、文档三个路径。其他平台即使已经有适配器，也需要按照当前消息类型和会话类型检查，不能用一个“支持媒体”的勾概括所有差异。

## 发不出去，也要让人看得见

一个渠道可能接受图片上传，另一个渠道只接受 URL。如果处理器给了一张只有 `data` 的图片，而目标接口只支持 URL，最糟的处理是直接返回。

从用户视角看，机器人好像回复完了，只是少了最重要的那张图；从处理器视角看，没有异常，也不知道交付缺失。

项目的媒体发送约定是：能发就发，不能发时给出明确文本提示。例如：

```text
[图片（本地文件，当前渠道无法发送）]
```

这只是中文表达示例，具体适配器的提示文案可能不同。关键是用户能知道发生了什么，而不是静默丢失。

我也不会为了“支持 URL-only”就把企业附件临时传到公开图床。公开地址会改变资料的访问边界；需要链接交付时，应当另外设计受控下载入口、授权与有效期。当前可见降级比擅自扩大文件可见范围更合适。

## 失败降级的代码，应该尽量保持用户原来的信息

支持原生上传的平台，可以先读取字节，再走自己的上传协议：

```python
async def _send_media(self, subject, media):
    try:
        data, mime = await self.load_media_bytes(media)
        resource_id = await self._upload_to_platform(data, mime)
        await self._send_with_platform_id(subject, resource_id)
    except Exception:
        logger.exception("Media delivery failed")
        label = self._get_media_label(media)
        url = self._get_media_url(media)

        if url:
            await self._send_text(
                subject,
                f"[{label}: {url}]",
            )
        elif media.data or media.local_path:
            await self._send_text(
                subject,
                f"[{label}: upload failed]",
            )
```

这是展示降级结构的示例，具体上传返回值和发送方法由平台决定。异常范围覆盖读取、上传和发送，因此日志需要保留失败阶段，才能分辨是本地文件不存在、平台拒绝上传，还是资源上传后发送失败。

内部调用 `_send_text` 也有原因：外层公共发送已经获取一次额度，适配器内部的降级属于同一次逻辑交付，不应重新绕回公共 reply 入口。

URL 回退并不保证用户可以访问。原地址可能是需要鉴权的临时链接，最终产品还应避免把带凭证的地址原样发进群里。对于不适合展示的地址，可以只提供清楚的附件失败提示和重试方式。示例表达的是“失败要可见”，具体可展示信息仍由平台和资料策略决定。

还有一种更难发现的情况：上传其实成功，发送请求返回超时。此时直接重试完整流程，可能产生重复资源或重复消息。若未来要做自动重试，应当利用平台提供的幂等能力或保存阶段状态，不能把所有错误都当作“之前什么都没发生”。

## 为什么我会把“处理成功”和“交付成功”分开记录

处理器生成了一份正确的摘要，不代表摘要文件已经到达用户。媒体路径天然有多个阶段：

| 阶段 | 成功说明什么 | 仍不能证明什么 |
| --- | --- | --- |
| 读取完成 | 系统拿到了附件字节 | 平台接受该内容 |
| 上传完成 | 平台保存了资源 | 消息已经发到目标会话 |
| 发送请求成功 | 平台接受了发送 | 终端用户已经阅读 |
| 降级文本成功 | 用户可见消息已发送 | 原附件已完整交付 |

第一版可以记录阶段日志，避免一个笼统的 success 掩盖附件缺失。后面如果业务确实需要追踪，可以设计交付结果对象，区分文本成功、附件失败和整体失败，再决定是否重试或通知维护者。

这项结果建模属于改进方向，并不是当前公共发送返回值已经提供的完整能力。文章里把它单独提出来，是因为它决定后续能不能可靠地回答“这份文件到底发出去没有”。

## 缓存和原始存储，清理责任为什么不同

缓存丢了通常可以重新下载；原始存储丢了，可能就失去了唯一一份结果。二者即使用同一套 save/read 接口，也不该默认使用同一种保留策略。

如果 URL 有效期很短，回源能力也会随着时间消失。缓存文件删除之前，要先判断它是不是仍然可恢复。对于处理器刚生成、尚未交付的文件，更不能简单按“最近没有读取”清掉。

我会给附件的保留规则明确责任人：网关负责传递字节，存储服务执行清理策略，业务任务决定某份结果是否仍需要保留。短期群聊 TTL 只限制讨论上下文，不替代文件保留期。

## 群聊缓冲里，文件也有自己的生命周期

上一篇讲到，被动讨论可以暂存在内存里。对文件而言，只保存下载链接未必够，因为链接可能在真正提问前失效。

公共入站准备流程会先根据群聊策略判断媒体是否值得保存：本轮处理需要的媒体保存；近期上下文确实会保留的被动附件也可以保存；历史关闭或只看 @ 的场景，避免无意义下载。

但“缓冲消息过期”不自动等于“磁盘附件也被删除”。这份仓库的媒体接口并没有提供完整的保留期清理机制。如果面向实际企业使用，存储容量、附件有效期、清理任务和访问审计，都需要在外层补设计。

本地文件系统后端的方法虽然声明为 async，内部仍使用同步文件读写。少量小文件时容易实现；大量大文件时，需要评估事件循环被阻塞的影响，再决定是否改为线程卸载或其他存储方式。

## 我会拿哪些组合做验证

只测“发一张图片成功”还不够。我会分别验证：

1. 三种来源同时存在，使用 `data`。
2. 只有存储键时，从后端读取。
3. 指定存储键但未配置后端，明确报错。
4. 只有 URL 时，下载内容，检查可选缓存。
5. 平台上传失败时，用户得到可见提示。
6. URL-only 消息类型收到本地数据时，不静默丢弃。
7. 群里先发文件再 @，短期上下文仍保留附件信息。

仓库的 `tests/test_channel.py` 包含来源优先级、缺少后端和缓存测试；`tests/channels/test_send_local_media.py` 检查多个渠道的本地媒体行为；`tests/test_media_integration.py` 是进一步核对媒体流转的入口。具体测试范围应以实际命令和环境为准，不能把 mock 单元测试当作真实平台投递证明。

这一篇可以结合公共媒体读取、存储后端接口和渠道自己的媒体发送实现阅读。代码省略了平台配置与部分校验，重点展示字节来源和错误边界。

## 回头看这五篇

这套设计从用户最普通的动作开始：发一句话、补充一句、等一个答案、在群里追问、附上一份文件。每一步都需要清楚的责任边界，也都存在不能靠抽象自动解决的现实条件。

如果把它继续做成企业项目，我会先选定一个入口和一个明确的知识问答场景，完成身份关联、资料授权与可观察的交付，再用真实使用反馈决定下一步。这样形成的设计记录，比先画一张涵盖全部平台的巨大架构图更有用。
