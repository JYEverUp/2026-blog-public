> 本系列以面向中国华能集团的企业知识助手为设计场景，业务对话均为示例。代码节选与结构示意用于说明设计原因、作用和取舍，省略了无关细节。

## 先从一个普通问题开始

假设同事在工作群里发了一句：“上次培训的资料在哪里？”

做一个演示并不难。接收消息，调用模型，把回答发回去，几十行代码就能串起来。可真要把它放进日常工作，问题马上多起来：有人用私聊，有人在群里补充一句话，有人只发了一张截图；模型检索资料要等一会儿，用户以为卡住了，又问了一次。

如果企业后面还要接入另一种聊天工具，难道把这整套逻辑再复制一份？

所以，我会先把需求缩小到一句话：**让同一套助手能力，通过不同消息入口稳定地收发内容。** 至于知识库如何检索、模型选哪个、业务操作要不要审批，是后面其他模块的责任。

企业名称也不能替代需求分析。使用什么办公平台、允许接入哪些群、资料权限如何确定，都需要实际调研。这里用企微、飞书等渠道说明设计，不假定客户真实使用了这些平台。

## 第一版，我会先做一个入口

一开始就同时接十个平台，开发时间会被鉴权、权限申请和回调配置分散。我更愿意选一个确认能用的平台，跑通“提问—处理—回答”这条链路，再用第二个平台检验抽象是否合理。

这个过程有三种常见选择：

| 做法 | 直接收益 | 后面要承担什么 |
| --- | --- | --- |
| 每个平台各写一个完整机器人 | 第一个版本最快 | 同一条业务规则要修改多处 |
| 做一个很大的统一接口，把所有平台能力装进去 | 表面上调用方式一致 | 接口里容易出现大量平台判断和空实现 |
| 统一消息语义，保留平台自己的传输方式 | 业务处理器容易复用 | 必须认真划清公共流程与协议差异 |

我会选第三种。它的价值在于，业务处理器收到的是“某个会话发来文字和图片”，不必知道这张图片在某个平台上叫什么字段。

## 中间放一个消息网关

可以把网关理解成一个接线员：接收不同入口的消息，整理成相同格式，再把处理结果送回原来的地方。

![消息网关与业务处理器的职责边界](/blogs/ai-gateway-01-architecture/architecture.svg)

[下载这张图的 Mermaid 源文件](/blogs/ai-gateway-01-architecture/architecture.mmd)

图中业务处理器后面的知识检索是场景设计，不是网关已经内置的能力。仓库中，调用方通过 `MessageProcessor` 注入处理逻辑；网关负责接入与交付。

我会给这几个部分明确分工：

- **平台适配器**：处理连接、鉴权和平台消息格式，执行真正的发送请求。
- **ChannelManager**：管理渠道生命周期、队列、worker 和会话锁。
- **BaseChannel**：组织公共入站步骤，处理默认事件交付、媒体读取和发送约束。
- **业务处理器**：理解问题、查询允许访问的资料、组织回答，并维护业务侧的对话。

这样，即使日后替换模型，平台连接也不必跟着重写。

## 最容易混淆的是“谁在说话”和“回复到哪里”

私聊时，这两个问题看起来是同一个问题：用户发来消息，回答给这个用户。

群聊时，它们就不同了。小李在资料群里提问，回复目标是这个群，作者仍然是小李。如果拿小李的用户 ID 当群聊会话目标，同一个群里的讨论就会被拆成几条互相看不到的对话。

项目的 `ChannelSubject` 表达回复目标：私聊用用户 ID，群聊用会话 ID。群成员的身份放在 `metadata.sender_id`、`metadata.sender_name` 中。

另一个名字也需要分清：`channel_session_id` 是平台连接会话，可能随重连变化，不能拿它当长期对话 ID。长期会话由业务处理器负责。

下面是一个概念示例，用来说明字段含义：

```python
message = InboundMessage(
    channel_id="office-bot-01",
    channel_type="feishu",
    channel_subject=ChannelSubject(
        subject_id="document-group",
        chat_type="group",
    ),
    content=[TextContent(text="培训资料在哪里？")],
    metadata={
        "sender_id": "employee-li",
        "sender_name": "小李",
    },
)
```

这些示例 ID 不对应真实员工、群组或平台凭据。

## 为什么要有一份中间模型，而不是直接传平台字典

把平台收到的 JSON 原样传给处理器，看起来少做了一次转换。但这种方便会慢慢传染：检索逻辑要读平台的用户字段，生成逻辑要猜图片字段，日志系统也要按不同平台找消息 ID。增加一个渠道时，需要检查的就不再是一个文件，而是整条业务链。

中间模型的作用，是把变化挡在入口。平台把自己的格式翻译完，后面的代码只面对稳定含义。下面是为了说明边界而简化的模型，并非完整生产定义：

```python
from dataclasses import dataclass, field
from typing import Literal

from pydantic import BaseModel, Field


class TextContent(BaseModel):
    type: Literal["text"] = "text"
    text: str


class ImageContent(BaseModel):
    type: Literal["image"] = "image"
    url: str = ""
    local_path: str | None = None


ContentPart = TextContent | ImageContent


@dataclass
class ChannelSubject:
    subject_id: str
    chat_type: str
    metadata: dict[str, object] = field(default_factory=dict)


class InboundMessage(BaseModel):
    channel_id: str
    channel_type: str
    channel_subject: ChannelSubject
    content: list[ContentPart] = Field(default_factory=list)
    metadata: dict[str, object] = Field(default_factory=dict)
```

这里值得关注的不是字段数量，而是三个选择。

首先，内容使用列表。因为一条消息可以同时包含“看一下这个报错”与一张截图，不能强迫它只能是文字或只能是图片。列表还能保留内容的先后关系，便于处理器按原始表达组织输入。

其次，`type` 使用有限取值。它让分支处理更明确，也方便在消息入口验证格式。类型模型能减少“图片部分缺少必要字段”这类错误，但它不会替你证明远程图片可下载、用户有权访问资料，后两者仍然需要运行时判断。

最后，平台路由扩展留在 metadata，而不是每遇到一个平台字段就给公共模型增加一项。这样公共结构不会越来越像所有平台字段的并集。代价也很明确：metadata 的类型约束比较弱。因此，适配器应把必需的路由字段解析清楚，业务代码不要到处读取不稳定的平台键。

## 为什么回复目标需要成为一个对象

一个简单的 `send(user_id, text)` 接口，在私聊演示里足够用。但实际发送可能还需要会话类型、最近一次消息标识、平台要求的回复上下文。如果这些信息散落在处理器参数里，主动通知和被动回复会越来越难区分。

把目标收进 `ChannelSubject`，可以让发送接口始终接收“目标 + 内容”。适配器负责解释目标上的路由信息，业务侧不用到处拼平台参数。

这也有一个重要限制：并非所有路由信息都能长期复用。群 ID 通常可以继续作为目标，一次回调带来的回复凭证却可能很快失效。定时发送培训提醒时，不能把上一次提问的临时凭证直接拿来重放。

因此，设计上要区分稳定目标和本轮上下文。它带来的收益不是少传几个参数，而是避免“给同一个人发消息”被误认为“重复上一次回复请求”。主动推送应重新解析发送路径，清理或更新只属于某一轮的字段。

## 一条消息进入系统后，会经历什么

前面的架构图回答“有哪些部分”，下面用飞书私聊中的一句“你好”，把启动、接收、调度、生成、回复串成一次完整过程。群聊和附件虽然不是这句问候的必经路径，也放在条件分支中，方便看清它们会在哪里介入。

### 第一阶段：先接好入口，再让消息进入队列

![启动、SDK 回调与安全入队](/blogs/ai-gateway-01-architecture/startup-receive.svg)

[下载本阶段 Mermaid 源文件](/blogs/ai-gateway-01-architecture/startup-receive.mmd)

启动阶段不只是“连上飞书”。媒体后端、队列和入队回调需要先准备好，适配器收到事件以后，才有明确的去处。worker 随后从队列消费，而不是由 SDK 回调直接等待整个 AI 回答。

完整图把通道注册、回调和后端绑定放在启动部分，是为了概括准备关系。具体实现中，通道既可以在管理器启动前注册，也可以在运行时动态添加；不能把图中的一条概括箭头理解为每次 `start()` 都会重新创建同一个账号配置。

用户发来“你好”后，SDK 回调先过滤机器人消息、检查重复事件，再提取平台字段。这样重复推送或机器人自己的消息，不必继续占用 worker 和业务处理资源。去重是入口的一道减负措施，并不等于整个系统已经实现严格的“只处理一次”。

接下来调用管理器的 `enqueue`。由于 SDK 回调可能来自自己的线程，安全入队的意义，是把真正的队列操作安排回 asyncio 事件循环。这个线程交接点只负责交接，不在回调中等待模型完成。

这种设计的作用，是让平台回调尽快返回，也让并发数量、排队和异常隔离集中到消费端管理。代价是从这一刻起，需要明确队列容量、满队列策略和关机时如何处理未消费消息，第二篇会继续展开。

### 第二阶段：先知道消息属于哪个会话，再准备业务输入

![worker 调度、媒体持久化与群聊触发](/blogs/ai-gateway-01-architecture/prepare-policy.svg)

[下载本阶段 Mermaid 源文件](/blogs/ai-gateway-01-architecture/prepare-policy.mmd)

worker 拿到的还是平台载荷，需要先调用 `parse_inbound`，得到统一的 `InboundMessage`。私聊示例里的 `subject_id = ou_user_001` 表示回复目标，不是所有消息都会使用某个员工 ID：群聊的目标应该是群会话。

为什么解析要发生在会话锁之前？因为只有知道消息属于哪个会话，才能找到应该竞争的那把锁。符合条件的连续消息可以在这里合并，然后按渠道实例和会话目标进入互斥处理。

调用 `handle_inbound(message)` 后，公共准备阶段执行平台预处理、记录目标与回复路由、按需保存附件，最后应用群聊策略。公共准备入口仍然可以调用解析方法；适配器遇到已经是 `InboundMessage` 的对象时直接返回，所以不需要再次解析原始 JSON。

媒体保存放在群聊缓冲之前，是因为一份未触发回答的附件，也可能成为下一次“总结刚才文件”的上下文。只留一个短期下载 URL，到了真正提问时可能已经失效；先保存字节，再记录存储键，才能让后续处理有稳定的内容来源。

但这不是无条件下载所有附件。媒体层会结合群聊策略判断是否需要保存：如果历史关闭、该消息也不会进入本轮处理，就应避免无用的网络请求和存储写入。

图中的 `alt` 把“看见消息”和“启动处理器”分开。群消息未触发时，可以暂存讨论并结束本轮；已经触发时，才把当前消息与必要上下文交给业务。这个判断位于模型调用之前，因此触发行为可以被配置和测试，不必让模型猜自己应不应该插话。

### 第三阶段：processor 是统一入口，Agent 是可选实现

![处理器与可选 Agent 后端的事件转换](/blogs/ai-gateway-01-architecture/processor-agent.svg)

[下载本阶段 Mermaid 源文件](/blogs/ai-gateway-01-architecture/processor-agent.mmd)

图里特意没有让 `BaseChannel` 直接调用模型。它面对的是 `processor(message)`，只要求处理器产生统一的回复事件。这个入口背后可以是规则查询、固定业务接口，也可以是调用 Harness Agent 的 AI 处理器。

如果选择 AI 后端，processor 负责把网关消息转换成 Agent 所需的请求：整理 `messages`，决定 `thread_id`，填入 `user` 与 `source`。这些字段有不同含义，不能因为当前私聊示例里值相近，就把用户身份、业务会话和消息来源当成同一个概念。

尤其是 `thread_id`，它决定业务侧历史归属。跨账号、跨群和跨平台是否应该共享历史，要由业务规则决定，再选取有足够隔离范围的键。平台连接重连时会变化的 `channel_session_id`，不应直接拿来承担长期对话身份。

下面只展示“把 Agent token 转成统一增量事件”这个接缝，其他事件类型和资源清理仍需按实际后端处理：

```python
async def agent_processor(message):
    request = build_request(message)

    async for chunk in agent.stream(request):
        if chunk.get("type") == "token":
            text = chunk.get("content", "")
            if text:
                yield MessageEvent.delta(text)

    yield MessageEvent.completed()
```

`build_request` 表示业务自己的输入转换函数。它不应该把未经授权的资料仅凭一个平台用户 ID 就加入请求，也不需要反过来理解飞书上传图片的接口。

模型和工具返回的事件，可能包括正文、思考、工具调用或工具结果。processor 把它们映射成网关能够理解的 `MessageEvent`，渠道再决定哪些可展示、如何展示。统一的价值在这个接缝上：底层 Agent 变了，平台发送代码不必跟着认识一套新事件。

完整图中的两个 `DELTA` 会先被默认公共交付流程积累，`COMPLETED` 到来时再发送剩余文字。片段按原样拼接，空格、标点和换行需要由处理器内容提供。对于具有原生更新能力的平台，也可以选择边生成边更新，这属于第三篇讨论的渠道交付策略。

### 第四阶段：回复与推送共享发送能力，但入口含义不同

![处理结果回复与主动推送的发送路径](/blogs/ai-gateway-01-architecture/reply-push.svg)

[下载本阶段 Mermaid 源文件](/blogs/ai-gateway-01-architecture/reply-push.mmd)

回复已有正文以后，公共入口 `reply_text(subject, text)` 先获取发送额度，再委托 `FeishuChannel._send_text` 调用平台 API。最终目标和回复上下文由 subject 上的路由信息决定，而不是让模型在答案里决定把消息发给谁。

限流放在公共入口，是为了让一次逻辑发送只获取一次额度。平台适配器内部拆分内容、执行媒体失败降级时，继续调用 `_send_*`，避免重新绕回公共入口，重复等待额度。

普通入站流程结束前，还要停止 typing 或超时等辅助任务、关闭事件流；成功时再更新一次性群聊上下文。对话锁则在本轮处理退出时释放，使同一会话后续消息可以继续。清理资源和业务成功是两个不同条件：资源应在相应退出路径释放，不能只在成功回答时清理。

主动推送走的是另一个入口。比如定时任务已经拿到“培训资料已更新”的内容，调用管理器的 `push_text`，由渠道执行发送，不需要为了投递现成文字再运行一次 processor。

这句话限定的是网关推送入口：如果业务要先让 AI 生成一份定时摘要，生成仍由调用方安排，生成完成后再调用 push。不能据此理解成主动消息永远不能包含 AI 内容。

推送也不会自动继承上一轮入站的全部语境。它需要使用有效的主动路由，清理只属于某一次回调的临时字段。如果主动业务还要修改与入站共享的会话状态，则应额外进入同一会话锁约定；单纯发送推送，并不等于已经获得了会话状态的互斥保护。

### 用这条链路定位一次“机器人没回复”

有了完整时序，排查也可以沿着明确边界推进，而不是一开始就怀疑模型：

| 看到的现象 | 先确认哪个边界 | 为什么 |
| --- | --- | --- |
| 平台发了消息，但没有入队记录 | SDK 回调、过滤与去重 | 消息可能根本没进入调度层 |
| 已经入队，迟迟没有开始处理 | worker、排队与会话锁 | 可能是在等待，而不是模型慢 |
| 准备完成，却没调用 processor | 群聊触发策略 | 被动消息可能按设计不回答 |
| processor 产生事件，聊天窗口仍无内容 | 缓冲刷新、额度与平台发送 | 生成成功和发送成功是两回事 |
| 回答已经出现，后续消息一直等待 | 本轮退出和锁释放 | 可能有任务没有结束或清理 |

图表达的是正常主线和主要条件分支，并未把所有断连、重试、取消与上传失败都展开。它的作用，是先把责任和交接点固定下来；具体失败模式再在所属模块处理，避免用一张过密的图代替清楚的模块边界。

## 公共流程写成骨架，是为了减少漏步骤

如果每个平台都复制一遍完整入站处理，最先出现的问题往往不是运行不了，而是某个平台忘了保存附件，另一个平台没有执行群聊策略，还有一个平台在异常时没有收尾。

这些问题难从“能不能发一条文字”发现，却会让相同功能在不同渠道表现不一致。我会把固定顺序留在公共入口，把变化留在明确的扩展点：

```python
async def handle_inbound(self, raw_payload):
    prepared = await self._prepare_inbound(raw_payload)
    if prepared is None:
        return

    message, subject = prepared
    succeeded = await self._process_inbound(message, subject)
    self._finalize_inbound(
        message,
        processing_succeeded=succeeded,
    )
```

这段骨架只有几个调用，却表达了一条约定：先准备，准备结果允许拦截；再处理，处理结束后根据结果收尾。

准备阶段为什么可以返回 `None`？因为“收到了一条合法消息”和“应该启动一次模型调用”不是同一件事。没有 @ 机器人的群聊，可以被记录为短期讨论，却不触发回答。用返回值明确表达这个结果，比在各平台方法里散落一组早退条件更容易检查。

为什么收尾依赖成功状态？因为短期上下文有时需要在成功处理后清理。如果业务失败还把相关讨论立即删掉，用户再问一次时，反而失去了理解问题所需的信息。

这段代码也暴露了边界：如果处理方法直接抛异常，没有返回状态，最后一行不会自然执行。默认处理实现需要在其责任范围内处理可预期错误；必须无条件释放的资源，则应该放在相应的 `finally` 中。流程骨架不是异常处理的替代品。

## 用依赖注入，让业务替换变成普通操作

“注入处理器”听起来像框架概念，实际使用可以很简单：管理器接收一个函数，需要处理消息时就调用它。

```python
from collections.abc import AsyncIterator, Callable

MessageProcessor = Callable[
    [InboundMessage],
    AsyncIterator["MessageEvent"],
]


async def echo_processor(message):
    text = "\n".join(
        part.text
        for part in message.content
        if isinstance(part, TextContent)
    )
    yield MessageEvent.text(f"已收到：{text}")
    yield MessageEvent.completed()


manager = ChannelManager(processor=echo_processor)
```

示例省略了连接配置与启动代码，只展示处理器的契约。先用回显函数，有一个很实用的作用：如果连回显都失败，问题更可能在平台连接、解析或发送；如果回显正常而知识问答失败，再看检索、模型和业务权限。

以后把 `echo_processor` 换成查询资料的处理器，渠道入口仍然保留。测试中也可以注入一个固定返回值的函数，不必为了验证“发送目的地是否正确”，真的去调用模型。

这里没有必要马上加入复杂的插件管理。只有处理器数量、依赖关系和动态替换需求真正增长时，再考虑更完整的注册和生命周期机制。一个明确的函数契约，已经能解决第一阶段的大部分解耦问题。

## 统一流程，也要给协议差异留出口

我喜欢这里的一个取舍：统一的是消息与处理步骤，没有硬把各平台的上传协议揉成一个方法。

例如，一处要求先上传得到资源 ID，另一处可能接受文件对象，某些消息类型又只能带公开 URL。这些差异真实存在，把它们藏起来并不会让它们消失。

因此，渠道自己的 `_send_media` 可以负责上传协议；读取待发送字节则通过公共的 `load_media_bytes` 完成。公共层解决可复用的问题，平台层保留必须不同的部分。

源码也并非每个地方都已经完全遵守同一条模板链路。当前企微为了流式回复直接重写了 `handle_inbound`，没有完整沿用默认的群聊准备与收尾流程。它提醒我：图表达的是公共主线，评估某个适配器时，还要检查其实际覆盖的方法。

## 企业场景需要另外补齐哪些东西

拿这个网关作为企业助手的接入层，是一个可行起点。但接收到了员工消息，不代表处理器就拥有读取全部企业资料的权限。

如果继续往实际部署推进，我会先补清楚：

- 平台身份如何关联企业身份，以及关联失败时怎么办。
- 检索资料前在哪一层执行权限检查。
- 日志保留哪些字段，是否包含原始正文。
- 哪些消息允许进模型，哪些操作必须人工确认。

这些属于方案下一层的设计条件，不能仅凭源码里有 `tenant_id`，就宣称已经完成企业级权限隔离。

## 设计的价值，要通过一次需求变化来检验

假设第一版只能回答文字，第二版要支持“读取员工发来的截图并解释报错”。如果职责分得合理，变化应当集中在三个地方：入口把图片转换为内容部分，公共媒体层提供字节，处理器选择能够理解图片的能力。发送文字回答的路径不需要大改。

再假设业务换了一种检索服务。只要处理器仍然接收统一消息、产生统一事件，连接、群聊触发和回复目标识别都不应该跟着换。

反过来，如果每次变更都要同时修改全部渠道，说明公共契约还没有稳定；如果所有新需求都要修改基类，说明基类可能承包了太多变化。

我会用下面这张表审视修改范围：

| 变化 | 主要修改位置 | 理应保持稳定的部分 |
| --- | --- | --- |
| 新增聊天平台 | 适配器与渠道注册 | 知识检索与业务规则 |
| 替换模型或检索服务 | 处理器 | 平台连接与格式转换 |
| 调整短期群聊策略 | 公共策略与配置 | 平台专属上传协议 |
| 切换附件存储方式 | 存储后端 | 统一的媒体读取入口 |

这里的“保持稳定”是一种设计目标，不是永远不改的承诺。接口如果无法表达真实需求，就应当修正接口。只是修正前需要先确认：变化来自共同语义，还是只属于一个平台的例外。

## 我会怎样验证这个边界

我会先用一个只回显消息的处理器验证接入，再替换成业务处理器。如果换处理器不需要修改平台协议代码，分工就基本站得住。

接着用第二个平台检查：能否把相同的文字、图片和群聊作者信息转换成统一模型；媒体上传能否只留在对应适配器中。仓库的 `tests/test_channel_registration.py` 还会检查注册项一致性，减少“写了适配器却漏了注册”的问题。

这一篇的实现线索可以从消息模型、公共渠道类、管理器和渠道注册入口依次阅读。文中的精简模型用于解释字段职责，不包含全部生产校验与平台配置。

到这里，我们只是把“从哪里来、交给谁、送回哪里”讲清楚。下一步，一个人连续发消息、另一个人同时提问时，调度才真正开始变得有意思。
